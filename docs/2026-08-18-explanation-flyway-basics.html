Section 1배경

프로그래머가 코드를 고칠 때는 마음이 편하다. 무엇을 언제 왜 고쳤는지 git이 전부 기억해주고, 마음에 안 들면 되돌리면 된다. 팀원과 코드가 어긋날 일도 없다. git pull 한 번이면 모두가 같은 코드를 본다.

그런데 애플리케이션에는 코드만 있는 게 아니다. 데이터베이스가 있다. 그리고 데이터베이스의 구조—테이블이 무엇이고 컬럼이 무엇인지—역시 시간이 지나며 계속 변한다. 이 변화는 누가 기억해주는가?

스키마 변경이라는 오래된 골칫거리

데이터베이스 마이그레이션 문제를 이미 겪어봤다면 이 절은 건너뛰고 다음 절로 가도 좋다.

상황을 구체적으로 그려보자. 회원 기능을 만들면서 member 테이블을 만들었다. 이메일과 닉네임이 있다. 한 달 뒤 휴대폰 번호를 받기로 했고, 다시 두 달 뒤에는 닉네임 길이 제한을 50자에서 100자로 늘리기로 했다.

당신의 노트북에서는 문제가 없다. ALTER TABLE을 직접 쳐서 바꾸면 되니까. 문제는 당신 말고 다른 데이터베이스들이다.

전통적인 해결책은 슬프게도 사람의 성실함이었다. "배포 전에 이 SQL 좀 돌려주세요"라는 메시지, 위키에 정리한 SQL 목록, 배포 체크리스트. 이 방식은 두 가지 이유로 실패한다. 첫째, 사람은 잊는다. 둘째, 잊었는지 아닌지를 확인할 방법이 없다. 운영 데이터베이스 앞에서 "이 SQL이 이미 돌았던가?"라고 묻는 순간이 반드시 온다.

문제의 핵심은 상태를 확인할 수 없다는 것이다. 데이터베이스는 지금의 모습만 보여줄 뿐, 어떤 변경들을 거쳐 여기까지 왔는지는 말해주지 않는다. git이 코드에 대해 해주는 바로 그 일을 아무도 안 해주고 있는 것이다.

ddl-auto가 해주는 것과 못 해주는 것

Spring과 JPA를 쓰면 이 문제가 마법처럼 사라지는 것처럼 보인다. 설정 한 줄이면 되기 때문이다. 

spring.jpa.hibernate.ddl-auto: update

이걸 켜두면 Hibernate가 엔티티 클래스를 훑어보고 실제 테이블과 비교해서, 부족한 것을 알아서 만들어준다. 필드를 하나 추가하고 앱을 재시작하면 컬럼이 생겨 있다. 마술 같다. 개발 초기에는 정말 편하다.

그런데 이 마술에는 조건이 붙어 있다. Hibernate는 더하는 것만 할 줄 안다.

하고 싶은 일ddl-auto: update의 실제 행동
컬럼 추가✅ 잘 해준다
테이블 추가✅ 잘 해준다
컬럼 이름 변경 (name → nickname)⚠️ nickname을 추가만 한다. name은 데이터를 안은 채 영원히 남는다
컬럼 삭제❌ 아무것도 안 한다
타입 변경 (VARCHAR(255) → TEXT)❌ 대개 무시한다
CHECK 제약, 인덱스, 트리거 관리❌ 범위 밖이다
기존 데이터 변환 (예: JSON 컬럼을 별도 테이블로 옮기기)❌ 애초에 불가능하다
"지금 이 DB는 어떤 변경들을 거쳤나?" 묻기❌ 알 방법이 없다
함정

마지막 줄이 진짜 문제다. ddl-auto: update는 데이터베이스를 암묵적으로 바꾼다. 변경 이력이 어디에도 기록되지 않으므로, 운영 데이터베이스가 정확히 어떤 모양인지는 직접 접속해서 눈으로 확인하는 수밖에 없다. 그리고 눈으로 확인한 것은 재현할 수 없다.

그래서 실무에서는 update를 쓰지 않는다. 대신 Hibernate에게서 스키마를 만들 권한을 아예 빼앗고, 그 권한을 기록을 남기는 도구에게 넘긴다. 그 도구가 Flyway다.

지금 acttub에서 벌어지고 있는 일

이 이야기가 추상적으로 들린다면, 이미 당신의 프로젝트에서 벌어지고 있는 일이라는 걸 알아두면 좋겠다. acttub-backend/src/main/resources/application.yaml에는 이 두 설정이 짝을 이루고 있다.

acttub-backend/src/main/resources/application.yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate          # Hibernate: "스키마 만들지 마. 맞는지 검사만 해."
  flyway:
    enabled: true                 # Flyway: "스키마는 내가 만든다."
    locations: classpath:db/migration/postgresql

그리고 그 db/migration/postgresql 디렉터리에는 파일이 열두 개 있다. 이것이 acttub 데이터베이스가 지금까지 걸어온 길 전체다.

Section 2직관

Flyway의 전부: 진도표와 세 줄짜리 알고리즘

Flyway를 처음 접하면 대단한 물건일 것 같지만, 실제로 하는 일은 놀랄 만큼 단순하다. 마법이 전혀 없다. 앱이 시작될 때 딱 세 가지를 한다.

① 진도표를 읽는다
데이터베이스의 flyway_schema_history 테이블을 조회한다 → "아, V5까지 했구나"
↓
② 해야 할 일 목록을 읽는다
classpath의 db/migration을 스캔한다 → "파일은 V1부터 V12까지 있네"
↓
③ 차이만큼 실행하고 기록한다
V6, V7, … V12를 버전 순서대로 실행하고, 하나 끝날 때마다 진도표에 한 줄씩 적는다
그림 3. Flyway의 알고리즘 전체. 한 문장으로 줄이면 "어디까지 했는지 데이터베이스에 적어두고, 아직 안 한 것만 순서대로 실행한다."
핵심 개념

Flyway는 데이터베이스의 현재 모습을 보고 판단하지 않는다. 오직 진도표에 뭐라고 적혀 있는지만 본다. 이 구분이 나중에 여러 동작을 이해하는 열쇠가 된다. 진도표에 "V5까지 완료"라고 적혀 있으면, 실제 테이블이 어떤 모습이든 Flyway는 V6부터 실행한다.

이 단순한 규칙에서 팀 협업이 자연스럽게 따라 나온다. 세 사람의 데이터베이스가 서로 다른 진도에 있더라도, 각자 앱을 켜기만 하면 전부 같은 지점으로 수렴한다.

신규 입사자빈 DB

checksum, 혹은 과거를 봉인하는 장치

이제 Flyway를 쓰면서 가장 먼저 만나게 될 에러를 이해할 차례다. 그리고 이 에러는 버그가 아니라 설계된 안전장치다.

checksum은 마이그레이션 파일 내용의 해시값이다. Flyway는 시작할 때마다 이미 적용된 파일들에 대해 지금 파일의 해시와 진도표에 적힌 해시를 비교한다.

V1 파일을 다시 해싱한다
현재 V1__create_member.sql의 내용 → -2044951807
↓
진도표의 checksum과 같은가?
기록된 값: -2044951807
↙ 같다      다르다 ↘
✓ 통과 — 다음 마이그레이션으로
V2부터 이어서 실행한다
 
✗ FlywayValidateException
Migration checksum mismatch for migration version 1 — 앱이 시작조차 하지 않는다
그림 5. 매 실행마다 벌어지는 검사. 공백 하나만 바꿔도 해시가 달라지므로 즉시 걸린다.

왜 이렇게 야박하게 구는 걸까? 잠깐 생각해보면 이유는 명백하다. 이미 실행된 SQL은 되돌릴 수 없기 때문이다.

당신이 V1을 어제 실행했다고 하자. 테이블은 이미 만들어졌다. 오늘 V1 파일을 고쳐서 컬럼 하나를 더 넣었다면, 그 변경은 당신의 데이터베이스에는 반영되지 않는다. 이미 V1은 "완료"로 기록돼 있으니 다시 실행되지 않으니까. 그런데 신규 입사자의 빈 데이터베이스에서는 고친 V1이 실행되어 컬럼이 생긴다. 결과적으로 같은 코드인데 두 데이터베이스의 모양이 달라진다. 그림 1의 악몽이 그대로 재현되는 것이다.

그래서 이런 규칙이 나온다

한 번 적용된 마이그레이션 파일은 글자 하나도 고치지 않는다. 고치고 싶으면 새 버전 파일을 하나 더 만든다. 오타 하나를 고치더라도 그렇다. acttub의 V5(컬럼 타입 확대)나 V6(길이 제한 해제)이 존재하는 이유가 바로 이것이다 — V1을 고치는 대신 새 파일을 쌓은 결과다.

이 원칙에서 나머지 규칙들이 줄줄이 따라 나온다.

  1. 롤백은 없다고 생각한다. 되돌리고 싶으면 "되돌리는 마이그레이션"을 새로 쓴다. (U 접두사의 Undo 기능이 있긴 하지만 유료 라이선스 전용이다.)
  2. 버전 번호는 증가만 한다. 뒤늦게 낮은 번호를 끼워 넣으면 사람마다 실행 순서가 달라진다.
  3. 엔티티 변경과 마이그레이션은 한 커밋에 넣는다. 따로 가면 다음 절에서 볼 validate가 앱을 멈춰 세운다.
  4. 운영 데이터베이스를 손으로 고치지 않는다. 손으로 고치는 순간 진도표와 실제가 어긋나고, Flyway는 어긋났다는 사실조차 알아채지 못한다 (Flyway는 진도표만 보니까).

SQL로는 불가능한 마이그레이션

마이그레이션 파일은 .sql만 있는 게 아니다. .java로도 쓸 수 있다. acttub에는 실제로 두 개가 있는데(V4, V7), 왜 굳이 자바여야 했는지를 보면 Flyway를 훨씬 깊이 이해하게 된다.

V4__Normalize_coaching_focus_axes가 한 일은 이렇다. 원래 coachings 테이블에는 result_focus_axes라는 JSON 컬럼이 있었다. AI가 분석한 "집중 축" 목록을 통째로 JSON 배열로 밀어 넣은 것이다. 이걸 제대로 된 관계형 테이블로 정규화해야 했다.

그림 6. V4가 수행한 변환. 한 행의 JSON 배열이 여러 행으로 펼쳐지고, 배열 안에서의 순서가 axis_order 컬럼으로 보존된다. 스키마만 바꾸는 게 아니라 기존 데이터를 읽어서 가공해 옮기는 작업이다.

Java 마이그레이션의 철칙

Java 마이그레이션 안에서 JPA 리포지토리나 엔티티를 쓰면 안 된다. 반드시 순수 JDBC(Connection, PreparedStatement)로 작성한다. 이유는 시점 때문이다 — 마이그레이션이 실행되는 순간의 데이터베이스는 과거의 스키마를 갖고 있는데, 엔티티 클래스는 현재 코드의 스키마를 가정한다. 위 V4를 엔티티로 짰다면, 나중에 Coaching 엔티티가 또 바뀌는 순간 과거의 마이그레이션이 깨진다. 마이그레이션은 작성된 시점에 박제되어야 한다.

validate가 채우는 마지막 구멍

여기까지 오면 Flyway가 데이터베이스 쪽은 확실히 책임진다는 걸 알 수 있다. 그런데 구멍이 하나 남아 있다. 개발자가 마이그레이션 쓰는 걸 깜빡하면?

엔티티에 phone 필드를 추가하고 마이그레이션은 안 썼다고 하자. Flyway는 아무 불만이 없다. 자기가 할 일(파일 목록대로 실행)은 완벽히 해냈으니까. 그리고 앱은 정상적으로 뜬다. 문제는 사용자가 회원가입을 시도하는 런타임에 터진다.

의존성 — 왜 두 개인가

build.gradle
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'

    // Flyway 본체. 이것만 있으면 마이그레이션이 동작한다.
    implementation 'org.flywaydb:flyway-core'
    // Flyway 10부터 DB 벤더별 지원이 별도 모듈로 분리됐다.
    // 이게 없으면 Postgres 접속 시 "Unsupported Database" 로 뜬다.
    implementation 'org.flywaydb:flyway-database-postgresql'

    runtimeOnly 'org.postgresql:postgresql'
    ...
}

Flyway 의존성이 두 줄이라는 점이 눈에 띌 것이다. 예전 버전(9 이하)에서는 flyway-core 하나면 충분했는데, Flyway 10부터 데이터베이스 벤더별 지원 코드가 별도 모듈로 쪼개졌다. Postgres를 쓰면 flyway-database-postgresql이 있어야 하고, 없으면 Unsupported Database: PostgreSQL이라는 다소 당황스러운 에러를 만난다. acttub도 똑같이 두 줄을 갖고 있다.

그 밖에 Spring Boot가 클래스패스에서 flyway-core를 발견하면 자동으로 Flyway를 실행한다. 별도의 설정 코드나 초기화 클래스가 필요 없다. 이것이 이 프로젝트에 Flyway 관련 자바 코드가 한 줄도 없는 이유다.

설정 — 권한을 넘기는 두 줄

src/main/resources/application.yaml
spring:
  jpa:
    hibernate:
      #   none     : 아무것도 안 함
      #   validate : 엔티티와 실제 테이블이 맞는지 검사만. 틀리면 앱이 안 뜬다  <-- 우리가 쓰는 것
      #   update   : 엔티티 보고 알아서 바꿈 (삭제/이름변경 불가, 실무 금지)
      #   create / create-drop : 매번 갈아엎음 (데이터 증발)
      ddl-auto: validate

  flyway:
    enabled: true
    locations: classpath:db/migration

    # [학습용] 아래는 전부 기본값이지만, 어떤 스위치가 있는지 알아두라고 적어둔다.
    # baseline-on-migrate: false   # 이미 테이블이 있는 DB에 Flyway를 나중에 붙일 때 true
    # validate-on-migrate: true    # checksum 검사 여부. false로 끄지 말 것(사고의 근원)
    # out-of-order: false          # 뒤늦게 낮은 버전이 들어와도 실행할지. 기본 false가 안전

logging:
  level:
    org.flywaydb: DEBUG            # Flyway의 판단 과정을 전부 찍는다

주석 처리해둔 세 옵션은 당장 쓰지 않지만 알아둘 가치가 있다. 특히 validate-on-migrate는 checksum 검사를 끄는 스위치인데, 앞서 본 에러가 귀찮다고 이걸 끄면 Flyway를 쓰는 의미가 대부분 사라진다. out-of-order 역시 팀 협업 중 버전이 꼬였을 때 유혹적으로 보이지만, 실행 순서가 사람마다 달라질 수 있어 기본값(false)을 유지하는 편이 안전하다.
